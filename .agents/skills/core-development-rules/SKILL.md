# 6대 절대 개발 원칙 (Core Development Rules)

본 문서는 사장님의 절대 지침으로, HDDGOD 프로젝트의 모든 코드 작성, 리팩토링, 버그 수정, 빌드 및 배포 작업 시 **무조건 최우선으로 준수**해야 합니다.

---

## 1. 짐작하지 말고 애매한 부분은 사용자에게 물어봐라
- 사용자의 요구사항에 모호한 점이나 복수의 해결 경로가 있을 때, AI가 자의적으로 추측하거나 임의로 단정하여 구현하지 않는다.
- 확실하지 않거나 부작용이 예상되는 부분은 즉시 사장님께 질문하여 의도를 명확히 확인한 후 진행한다.
- "이렇게 하면 되겠지"라는 짐작 기반 코딩은 절대 금지한다.

## 2. 시킨 것만 코딩하고, 200줄 짰는데 50줄로 줄어들면 다시 짜라
- 사용자가 요구한 작업 범위만을 정밀하게 구현한다.
- 기존에 정교하게 예외 처리, 동기화, 로깅, 안전장치가 갖추어져 있던 코드를 리팩토링한다는 핑계로 임의로 단순화하거나 압축하여 200줄짜리 코드가 50줄로 쪼그라들었다면 즉시 롤백하고 원본의 견고성을 유지한 채 다시 짠다.
- 안전장치, 예외 분기, 로깅, 락(Lock) 메커니즘을 절대로 누락시키지 않는다.

## 3. 시키지 않은 코드는 건들지 마라
- 요청받지 않은 다른 모듈, 함수, 설정값, UI 요소를 임의로 수정하거나 "개선"하려 들지 않는다.
- 변경이 필요한 최소 단위의 파일과 라인만을 수정하며, 건드리지 말아야 할 정상 동작 코드는 1바이트도 건드리지 않는다.
- 사이드 이펙트(부작용)를 최소화하고, 수정된 부분만 독립적으로 검증 가능하게 한다.

## 4. 성공 기준을 먼저 정하고 실행해라
- 코드를 수정하거나 기능을 추가하기 전에, **"어떤 상태가 되어야 성공인가?"**라는 명확한 검증 기준(체크리스트)을 먼저 정의한다.
- 단순 "코드가 에러 없이 돌아갔다"가 아니라, 실제 PC 상태, 패킷 송수신 수치, 화면 표출 여부, 프로세스 동작 상태 등 객관적인 데이터로 성공 여부를 입증한다.
- 검증 기준을 통과하기 전에는 작업을 완료되었다고 보고하지 않는다.

## 5. 해도 잘 안 되면 중간에 멈추고 상황 보고하고 조언을 구하고 필요한 정보를 요청해라
- 오류가 반복되거나 예상대로 작동하지 않을 때 혼자서 무리하게 땜질식 수정을 반복(삽질)하지 않는다.
- 즉시 작업을 멈추고:
  1. 현재까지 시도한 내용
  2. 발생한 구체적인 에러/증상
  3. 막힌 원인에 대한 분석
  을 사장님께 솔직하고 명확하게 보고한다.
- 필요한 추가 정보(로그, 캡처, 사장님의 확인 등)를 요청하고 조언을 구해 방향을 재설정한 뒤 진행한다.

## 6. 에이전트 추가가 필요시 제시해서 업무 효율성을 높여라
- 복잡한 대규모 리팩토링, 심층 리서치, 병렬 코드 분석 또는 교차 검증 등 다각적인 분업이 효과적인 작업의 경우, 단일 에이전트 혼자 시간을 끌지 않는다.
- 전문 서브에이전트(리서처, 테스터, 코드 리뷰어 등)의 분업 협업이 유리하다고 판단될 때 사장님께 적극적으로 에이전트 추가를 제시하고 승인을 얻어 병렬 처리함으로써 개발 속도와 업무 효율성을 극대화한다.
